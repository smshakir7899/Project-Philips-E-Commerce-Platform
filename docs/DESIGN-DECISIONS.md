# Engineering Decisions (and the alternatives considered)

The original brief left these points open. Each entry records the choice made and the reason for it, so you can
defend it in an interview.

| # | Decision | Alternatives | Why |
|---|---|---|---|
| 1 | **Orchestrated saga** in order-service (sync Feign for reserve/pay, Kafka for follow-up effects) | Pure choreography (every step an event) | The customer waits for checkout anyway, and orchestration keeps the state machine in one class (`CheckoutService`), which is easier to reason about and test. Kafka is still used where coupling should be loose: commit, release, refund, cart clearing and notifications. |
| 2 | **Transactional outbox** + polling publisher | `kafkaTemplate.send()` inside `@Transactional`; Kafka transactions; Debezium CDC | Calling Kafka directly from a DB transaction is a *dual write*: either side can fail independently. The outbox makes "state change + event" atomic in MySQL. Polling with `FOR UPDATE SKIP LOCKED` lets several instances share the work. CDC is the production-grade evolution, but it needs Kafka Connect. |
| 3 | **Idempotent consumers** (`processed_event` written in the same TX) | Kafka exactly-once semantics | EOS only covers Kafka-to-Kafka flows; our side effects are MySQL writes. At-least-once delivery plus idempotency gives effectively-once processing and survives replays from the DLT. |
| 4 | JSON **String** payloads + explicit `ObjectMapper` mapping | `JsonSerializer`/`JsonDeserializer` with type headers; Avro + Schema Registry | Easy to inspect in Kafka UI, there is no coupling to Java class names in headers, and poison messages fail in the listener (where the DLT can capture them) instead of in the deserializer. Avro/Schema Registry would be the next step for schema evolution. |
| 5 | Retry `FixedBackOff(1s × 3)` then **DLT** (`<topic>.DLT`), central DLT store in notification-service with replay | Retry topics (`@RetryableTopic`) | Blocking retries are simple and preserve per-key ordering. Non-blocking retry topics trade ordering for throughput; this is worth discussing in an interview. |
| 6 | **Pessimistic locking** for stock reservation; **optimistic** `@Version` elsewhere | Optimistic locking with retries; Redis-based counters | Reservation is a high-contention, must-not-oversell operation, and a short row lock in a sorted order (no deadlocks) is the simplest correct solution. Admin edits are rare, so optimistic locking avoids holding locks. |
| 7 | **Idempotency-Key** header for checkout; derived key `PAY-<orderNumber>` for payment | Client-side dedupe only | Retries after network failures are normal (Feign retry, user double-click, gateway retry), so the server must deduplicate. |
| 8 | Payment timeout ⇒ order `PAYMENT_FAILED` + compensation (refund on late success) | Mark order `PAYMENT_PENDING` and reconcile later | The customer gets a definite answer quickly. The "unknown outcome" is resolved by payment-service: a cancel request on a `PROCESSING` payment sets `cancelRequested`, so a late success is refunded automatically. |
| 9 | Remote calls **outside** DB transactions; each local step is a separate `@Transactional` bean method | One big `@Transactional` checkout | A transaction cannot span services (no 2PC). Holding a DB connection during HTTP calls exhausts the pool under load. A separate bean also avoids Spring's self-invocation proxy pitfall. |
| 10 | **Explicit cache-aside** with `StringRedisTemplate` | `@Cacheable` | It makes TTL, keys, hit/miss counters, failure fallback and invalidation visible and measurable. `@Cacheable` hides these details. |
| 11 | **Versioned namespace** invalidation for list/search caches (`INCR product:v1:list-version`) | `KEYS product:*` then `DEL`; `@CacheEvict(allEntries)` | `KEYS` is O(N) and blocks Redis. A version bump makes every old page key unreachable in O(1), and those keys then expire through their TTL. |
| 12 | Invalidate **after commit** | Evict before or inside the transaction | If you evict before commit, a concurrent reader can repopulate the cache with the old row before the commit lands, leaving stale data for the full TTL. |
| 13 | Baseline vs optimized product reads selected by `app.product.query-mode` (`@ConditionalOnProperty`) | Git branches; commented-out code | Both implementations compile, are tested and can run against the same database, so the benchmark compares like with like. |
| 14 | **Flyway** + `ddl-auto: validate` | `ddl-auto: update` | Reviewable, versioned SQL (including index justifications), and Hibernate validates that the entities match the schema. |
| 15 | **config-server native** backend (`./config-repo`) | Git backend | Works offline. Switching to Git only means setting `spring.cloud.config.server.git.uri`. |
| 16 | One MySQL server, **six schemas** locally | One container per DB | Saves memory on a laptop while keeping the "database per service" ownership boundary (separate schemas, separate credentials possible, no cross-schema joins). In AWS you would use RDS, possibly one instance per service. |
| 17 | Simulated payment gateway with deterministic **test tokens** | Stripe test mode | Runs fully offline with no credentials, and every failure mode (decline, timeout, gateway error) can be reproduced on demand. It is clearly labelled as a simulation. |
| 18 | No authentication | Spring Security + JWT/OAuth2 at the gateway | Out of the resume scope. The gateway is the place to add it (`spring-boot-starter-oauth2-resource-server`), and `customerId` would come from the token instead of the request. |
| 19 | AWS SDK v2 `DefaultCredentialsProvider` | Access keys in config | Locally it uses MinIO credentials from environment variables. On EC2 it picks up the instance-profile role automatically, so no keys are ever stored. |
| 20 | Gateway Swagger aggregation | Separate Swagger per service only | One URL (`:8080/swagger-ui.html`) shows every service, and each service still exposes its own UI. |
